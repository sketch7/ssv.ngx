# ssv.ngx — Workspace Guidelines

`ssv.ngx` (`@ssv/ngx`) is an Angular 21 Nx monorepo publishing two independent, general-purpose Angular
utility libraries to the public npm registry under the `@ssv` scope. Unlike the `@arcane/ngx.*` libraries,
these carry no Arcane domain knowledge — they're consumed by Sketch7's Arcane frontends
(`sketch7.arcane.cosmowrench`, `sketch7.arcane.blueprint.client`, `sketch7.arcane.ngx`) and by anyone else,
either from npm or via pnpm workspace linking during local cross-repo development. `apps/test-app` is a
dev harness that exercises both libraries side by side; it is not published.

## Libraries

| Package             | Role                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------- |
| `@ssv/ngx.command`  | Command pattern — encapsulates an action plus its `isExecuting`/`canExecute` state     |
| `@ssv/ngx.ux`       | Viewport/responsive utilities — breakpoint matching, viewport data, SSR device sizing  |

**No cross-dependencies between the two libraries** — each publishes and versions independently, and
`@nx/enforce-module-boundaries` fails lint on any import across them. `apps/test-app` may depend on both.

## Commands

Package manager is **pnpm** (`preinstall` enforces it via `npx only-allow pnpm`). Node `>=24.14.0`
(volta-pinned to `24.14.0`), pnpm `9.15.9`.

```bash
pnpm install

# Dev harness
pnpm start                # = pnpm test-app = nx serve test-app

# Build (patch-pkgjson strips the @ssv/source condition, run automatically as part of the Nx release/publish task graph — see Known Pitfalls)
pnpm build                # nx run-many -t patch-pkgjson (builds, then patches dist package.json)

# Test (Vitest, one project per library)
pnpm test                 # nx run-many -t test

# Lint
pnpm lint                 # nx run-many -t lint

pnpm clean                # remove dist/
pnpm nx reset             # clear the Nx cache when builds/tests seem stale
```

Single-library equivalents (prefer these when iterating on one lib):

```bash
pnpm nx build @ssv/ngx.command
pnpm nx test @ssv/ngx.command
pnpm nx lint @ssv/ngx.command

# The root vitest.config.ts registers ./libs/* as vitest projects, so specs can also be run directly
pnpm vitest run libs/ngx.command/src/command.spec.ts
pnpm vitest run --project="@ssv/ngx.command"
```

**Always run tasks through `nx`** (`nx run`, `nx run-many`, `nx affected`), prefixed with `pnpm`/`npx`
rather than a globally installed CLI. Never guess CLI flags — check `--help` or the Nx docs first.

### Release & publish

```bash
pnpm pre-release-build    # nx release version $VERSION (expects $VERSION)
pnpm release              # CI only: nx release publish (patch-pkgjson runs automatically first)
```

- `nx.json` `release.projects` is `["libs/*"]`. Library `package.json` versions are `"0.0.0-PLACEHOLDER"`
  in source and are stamped by `nx release version`; the root `package.json` version (`private: true`) is
  the workspace's own version. **Never edit library versions manually.** Each library also has a generated
  `src/version.ts` exporting `VERSION`.
- CI (`ci.yml`) and CD (`cd.yml`) both trigger on `main`, `v*`, and `workflow` branches; CD also runs on
  manual dispatch. Both wrap reusable workflows from `sketch7/.github` — see the
  `arcane-ci-cd-workflows` skill before editing them.
- Library majors are driven by API breaking changes, not Angular majors: v3/v4/v5 all declare
  `@angular/core >= 17.0.0` as a peer (the workspace itself builds and tests on Angular 21); only the
  older v2 (Angular 10+) and v1 (Angular 4–9) lines track Angular versions. Per-library compatibility
  tables are in each README; per-major breaking changes in `CHANGELOG.md`.

## Architecture

### Library layout (uniform across both `libs/*`)

```
libs/{lib}/
  index.ts             # re-exports ./src/index — the ng-packagr entry point
  src/index.ts         # the ONLY public surface — hand-curated named exports
  src/version.ts       # generated by `nx release version`
  src/*.ts             # implementation — directives, services, models, utils
  src/*.spec.ts        # co-located Vitest specs (no separate test tree)
  src/test-setup.ts    # Angular test env bootstrap
  package.json         # publishable manifest; version is "0.0.0-PLACEHOLDER"
  project.json         # Nx targets: build (@nx/angular:package), test (@nx/vitest:test), lint
  ng-package.json, tsconfig*.json, vitest.config.ts
  README.md            # per-library usage docs
```

**Public API discipline**: consumers only get what `src/index.ts` re-exports, as explicit named exports —
don't rely on deep imports and don't `export *` at that level. `libs/ngx.ux` nests `viewport/` (and
`viewport/viewport-data/`) submodule folders, each with its own `index.ts` barrel re-exported upward — the
pattern for splitting a larger library into sub-features while keeping one public entry point.

Path aliases `@ssv/ngx.command` and `@ssv/ngx.ux` resolve to `libs/*/src/index.ts` in the workspace
(`tsconfig.base.json`).

### Command pattern (`libs/ngx.command`)

This repo is the reference implementation of the pattern used across Sketch7 apps for button/action state.

- `command(execute, canExecute?)` — factory function (never `new Command()`), requires an injection
  context and auto-injects `DestroyRef`, so no manual cleanup. Handles sync and async
  (`Promise`/`Observable`) execute functions transparently.
- State is signals: `$isExecuting`, `$canExecute`. The plain `isExecuting`/`canExecute` getters still
  exist but are `@deprecated` — new code reads the `$`-prefixed signals.
- `canExecute` accepts a `Signal`, `Observable`, plain function, or `boolean`;
  `canExecuteFromNgForm()` / `canExecuteFromSignals()` adapt forms.
- `SsvCommand` (`[ssvCommand]`) / `SsvCommandRef` directives wire a command to a control, with
  `[ssvCommandParams]` for arguments — a single array argument must be double-wrapped (`[[arr]]`) or it
  spreads into multiple params.
- `commandAsync` and the `Command` class remain exported but are `@deprecated` in favour of `command()`.

Full patterns live in the `ssv-ngx-command` skill; API docs in `libs/ngx.command/README.md`.

### Viewport utilities (`libs/ngx.ux`)

- `ViewportService` exposes `sizeType`/`viewportSize` signals plus `sizeType$`/`size$` observables
  (throttled) and `*Snap$` (unthrottled) variants.
- `*ssvViewportMatcher` / `*ssvViewportMatcherVar` structural directives render by breakpoint condition,
  with tuple syntax (`['>=', 'xlarge']`) as the recommended form.
- `ViewportDataService` + the `ssvViewportData` pipe resolve per-breakpoint data via a
  `ViewportDataMatchStrategy`.
- `provideSsvUxViewportOptions()` configures breakpoints/polling; `withViewportSsrDevice()` supplies a
  device type for SSR, where no real viewport exists.

Full patterns live in the `ssv-ngx-ux` skill; API docs in `libs/ngx.ux/README.md`.

## Conventions

### TypeScript / Angular

- `inject()` over constructor injection; private fields use the `#` prefix (`#renderer = inject(Renderer2)`).
- Standalone only — existing `*.module.ts` files (`command.module.ts`, `ux.module.ts`) are kept for
  backward-compatible consumers, not a pattern to extend.
- Signals over decorators for state: `signal()`/`computed()`/`effect()`, `DestroyRef` over `ngOnDestroy`.
  Note this is about state, not inputs — older directives such as `viewport-matcher.directive.ts` still use
  `@Input()` setters, and that's fine; check the surrounding file's style before "modernizing" on sight.
- Double-quoted strings (`@stylistic/ts/quotes`), tabs for indentation (`.editorconfig`).
- Prefer `unknown` over `any`; use the exported type guards (`isCommand()`, `isCommandCreator()`).
- Custom `ssv` selector prefix (`prefix: "ssv"` in each `project.json`); `@angular-eslint/directive-selector`
  is disabled accordingly.
- `isolatedModules: true`, target ES2022, `moduleResolution: "bundler"`.
- Deprecate rather than remove: keep a `/** @deprecated Use {@link x} instead. */` re-export alias so
  consumers don't break.

### Tests

- Framework is **Vitest 4** via `@nx/vitest:test` + `@analogjs/vite-plugin-angular` — never Jest, despite
  `nx.json`'s `generators.*.unitTestRunner: "jest"` default (each `project.json` overrides it; a newly
  generated project must be switched to `@nx/vitest:test` by hand).
- Specs are `*.spec.ts` co-located with the source file they test.
- Test env is bootstrapped per library in `src/test-setup.ts` via `@analogjs/vitest-angular/setup-zone` +
  `getTestBed().initTestEnvironment(BrowserTestingModule, platformBrowserTesting())`.
- Root `vitest.config.ts` sets `globals: true` and `environment: "jsdom"`, and registers `./libs/*` as
  projects; each library's own config sets `test.name` to its npm package name.
- See the `arcane-testing-principles` and `arcane-ngx-testing` skills for house testing conventions.

## Known Pitfalls

### The `@ssv/source` export condition must be stripped before publish

Each library's `package.json` declares `"exports": { ".": { "@ssv/source": "./index.ts" } }` so sibling
repos can link against live source (via `pnpm-workspace.yaml` overrides in cosmowrench/blueprint.client).
ng-packagr copies `exports` verbatim into `dist`, so a tarball published without stripping it points
consumers at an `index.ts` that isn't in the package — and consumers set the condition unconditionally,
which breaks the **registry** path for everyone.

`tools/patch-pkgjson.mjs` (idempotent) applies small, targeted patches to built `dist/**/package.json` files
— stripping `@ssv/source` is the first one; add more patches to its `PATCHES` array rather than writing a new
script/target. It's wired into the Nx task graph, not chained by hand in npm scripts: `nx.json` gives every
library a `patch-pkgjson` target (`dependsOn: [{ target: "build", params: "forward" }]`), and
`nx-release-publish` depends on that target. So `nx release publish` — and therefore `pnpm release` / CD —
cannot publish a package without patching it first, regardless of build caching or which script triggered
it. Don't reintroduce ad hoc `npm run patch-pkgjson && ...` chaining in root scripts. The tool mirrors the
one in `sketch7.arcane.ngx` — keep the two in sync.

### Flat `node_modules` is deliberate

`.npmrc` sets `node-linker=hoisted`, so there are no per-library `node_modules`. A nested `node_modules`
under `libs/*` shadows resolution for sibling consumer workspaces that link this repo's source, producing
duplicate Angular DI tokens (two `InjectionToken` instances, "wrong instance of injected service" errors).
See the `arcane-ngx-workspace-linking` skill for the consumer side of this.

### Angular 21 `TemplateRef` typing breaks the matcher's `else` clause

`*ssvViewportMatcher="...; else foo"` raises `TS2322` under Angular 21's `TemplateRef` typing. The input
(`ssvViewportMatcherElse`) exists and works at runtime — it's a compile-time typing problem. The workaround
used throughout this repo is two directives with complementary conditions instead of an `else`:

```html
<!-- ❌ TS2322 -->
<div *ssvViewportMatcher="['>=', 'large']; else smaller">…</div>

<!-- ✅ -->
<div *ssvViewportMatcher="['>=', 'large']">Large</div>
<div *ssvViewportMatcher="['<', 'large']">Smaller</div>
```

### Custom breakpoints replace, never merge

`provideSsvUxViewportOptions({ breakpoints: {...} })` replaces the default breakpoint map wholesale — a
partial map silently drops the sizes you left out. Supply the complete set.

# General Guidelines for working with Nx

- When running tasks (for example build, lint, test, e2e, etc.), always prefer running the task through `nx` (i.e. `nx run`, `nx run-many`, `nx affected`) instead of using the underlying tooling directly
- You have access to the Nx MCP server and its tools, use them to help the user
- When answering questions about the repository, use the `nx_workspace` tool first to gain an understanding of the workspace architecture where applicable.
- When working in individual projects, use the `nx_project_details` mcp tool to analyze and understand the specific project structure and dependencies
- For questions around nx configuration, best practices or if you're unsure, use the `nx_docs` tool to get relevant, up-to-date docs. Always use this instead of assuming things about nx configuration
- If the user needs help with an Nx configuration or project graph error, use the `nx_workspace` tool to get any errors

# CI Error Guidelines

If the user wants help with fixing an error in their CI pipeline, use the following flow:
- Retrieve the list of current CI Pipeline Executions (CIPEs) using the `nx_cloud_cipe_details` tool
- If there are any errors, use the `nx_cloud_fix_cipe_failure` tool to retrieve the logs for a specific task
- Use the task logs to see what's wrong and help the user fix their problem. Use the appropriate tools if necessary
- Make sure that the problem is fixed by running the task that you passed into the `nx_cloud_fix_cipe_failure` tool
